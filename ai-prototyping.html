Making the system readable by AI

I set the direction for an MCP server, built by the team, that lets AI tools search and pull the design system's documentation. AI tools get the current docs instead of guessing.

I wrote two skill files that AI tools load before they work. One sets the system's voice, plain-language rules, terminology and a self-check for content. The other covers approved terms and how the system changed between versions.

A method for coded prototypes

In my current role on the child care funding assessment team, I built a template that lets designers make working, coded prototypes with the design system and AI tools, so they design with the same components production services use.

How a designer uses it

  1. Copy the template, open it in an AI coding tool and say "Set this up." The tool asks a few questions, gets the prototype running and turns on a live link.
  2. Describe changes in plain language, such as "add a page that asks for the applicant's address."
  3. Each change gets its own preview link. Merging it updates the shared prototype.
  4. Snapshots keep a fixed version for research sessions.

Skills that carry Government of Alberta standards

Skills are written instructions that the AI tool reads when they're relevant to what a designer has asked. They come with every copy of the template, so designers don't set them up or call them by name. Teams can open them and edit them to suit how they work.

I wrote the skill files for design workflow, documentation, user stories, visual design and content design. Four more came from the design system's own AI tools, and I adapted one of them. They make the AI tools follow the same standards for every designer, the same job a design system does for components.

  • Design workflow. When a designer is working on a layout, the AI tool draws its proposed solutions as ASCII diagrams for the designer to review. Text is quick to generate, so the designer can weigh options without breaking the flow of the work.
  • Documentation. Each area of the prototype has a requirements doc, updated in the same pull request as the change so it never falls behind. Every point is marked as a decision, assumption, open question or prototype-only shortcut, with who decided and when. Old decisions are replaced, not deleted, so you can see what changed and why.
  • User stories. Jira stories are drafted from the prototype and its requirements docs, with links to the preview and the doc. The team then refines them together as usual.
  • Content design. Labels, messages, errors and guidance are written for the right reader: plain language for citizens, denser wording for workers.
  • Visual design. Heading and text sizes, text colour and spacing stay consistent from screen to screen. Designers also use it when a screen looks off or feels cramped.

The reasoning in the requirements docs has to come from the designer, their Miro boards and Confluence. A doc an AI tool writes just by reading the code describes the screens, but not why they're that way.

Opening it up to other teams

I wrote a get-started guide so designers across the Government of Alberta can use the method, not only my team. It covers getting access, starting a prototype from the template in React or Angular, the built-in skills, connecting Jira, Confluence, Miro and Figma, and how I work, such as one group of changes per pull request. Five more projects have started from the template so far.
