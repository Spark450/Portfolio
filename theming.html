Theming without forking

A minister-priority service needed a look that was very different from the standard Alberta style, on a fixed deadline. The easy answer was to copy the components and restyle them, which would have cut the service off from every future fix. Instead we added design tokens at the component level, so it could look different and still get every update.

I set one rule for every decision: how does this help the whole system, not just this one team?

Sorting every component

We went through each component the portal needed and put it in one of five groups. The group decided how much the core system had to change.

GroupWhat it meantExamples
No changeExisting options were enoughTable
Style through tokensNew component-level tokens, no new code pathsCallout, accordion, container, button, side menu
New behaviourA small feature added to the core componentHeader menu button
New core componentBuilt for the portal, useful to everyoneDrawer
ExperimentalToo different for the core, kept in a separate package with its own lifecycleForm stepper

What changed

  • Delivered earlyIt let the portal team ship more than originally planned.
  • No forkThe portal still runs on the core system and gets every fix.
  • A reusable patternComponent-level tokens became the answer for any service that needs its own look.

The same approach for dark mode

Several teams were building their own dark modes, for example for first responders who need less screen glare. Each one was a different take on the Alberta brand. I wrote the strategy for one shared version: an experimental theme first, a one to three month trial with structured feedback, then a review with the government's communications team before anything goes to production.
